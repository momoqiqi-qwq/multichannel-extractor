# 0.8.1 用户体验与代码结构复审

## 结论

当前版本功能覆盖较完整，但主工作区的信息密度、不可操作控件的反馈方式、平台能力提示和构建可复现性仍是最明显的风险。下一版不建议立刻扩充大量解压功能，先做一轮“可用性与可发布性”收口更划算。

## 本轮已落地的体验修复

- 消除 Claude 通道按钮的操作死路。
- 没有成功解压结果时允许直接选择项目文件夹。
- 增加操作进行中状态，避免重复点击。
- 统一通道工具与总设置工具的目录选择行为。
- 更新界面说明，让用户知道按钮会如何选择目录。

## 建议优先优化的用户体验

### P0：让所有禁用状态可解释、可恢复

当前界面仍有不少仅通过 `disabled` 表达不可用的控件。应统一增加原因说明，并尽量提供直接修复入口。例如“打开目录”不可用时，可提示先选择目录；“开始全部”不可用时，应明确是队列为空、目录缺失还是任务正在运行。

建议抽象一个 `ActionAvailability` 模型：

- `enabled`
- `reason`
- `recoveryAction`
- `severity`

组件只负责展示，业务层负责计算原因。

### P0：显示 Claude 工具真实状态

项目辅助区域应直接显示：

- 当前平台是否支持一键启动；
- Claude CLI 是否可用及版本；
- 当前工作目录；
- DAT 是否存在；
- 启动会使用的固定命令。

不要让用户点击后才从错误 Toast 得知平台或 CLI 不支持。

### P1：降低通道展开区的信息密度

`ChannelCard.vue` 同时承载队列、输出、层级、收件规则、高级选项、项目工具、预设与清理动作。建议把展开区改为 3 个轻量页签：

1. 输出与层级
2. 自动化与收件
3. 工具与维护

默认只展示当前最需要的内容，避免用户在窄窗口或高缩放下寻找按钮。

### P1：替换 `window.confirm`

项目中多处使用浏览器原生确认框。它会阻塞渲染、样式不可控、无法展示结构化风险信息，也不利于键盘与辅助技术。建议复用统一的应用内确认对话框，并支持：

- 风险等级；
- 影响范围摘要；
- 默认焦点；
- “不再提示”设置；
- 需要输入名称的高风险确认。

### P1：完成后的下一步操作

成功 Toast 可提供上下文动作：

- 打开目录；
- 复制路径；
- 用 DAT 打开 Claude；
- 查看任务详情。

目前成功信息主要是文本，用户还需要回到卡片寻找下一步按钮。

### P2：可访问性与视觉层级

- 不要只依赖鼠标悬停 `title` 解释关键行为。
- 检查小字号说明文本在 125%/150% 缩放下的可读性。
- 为忙碌状态补充 `aria-live` 或状态文本。
- 确保图标按钮拥有稳定的 `aria-label`。
- 将危险动作与常规动作在位置和视觉上进一步分离。

## 代码结构发现

### 1. `channels.ts` 已增长到约 1236 行

它仍承担工作区状态、导入、任务运行、事件映射、持久化、对话框和多个子模块装配。建议拆成：

- `channelWorkspace.ts`：通道 CRUD、排序、折叠、分类；
- `channelImports.ts`：文件选择、检查、重复策略、自动开始；
- `taskRuntime.ts`：提交、暂停、继续、取消、事件处理；
- `workspacePersistence.ts`：序列化、迁移、节流持久化；
- `channels.ts`：只作为组合门面。

### 2. `AppSettings` 是 94 个字段的扁平接口

字段继续增长会导致迁移、默认值、设置页和持久化代码同步成本很高。建议按领域分组：

- `appearance`
- `behavior`
- `output`
- `reliability`
- `inbox`
- `projectTools`
- `retention`

迁移层可继续兼容旧扁平格式，再逐步切换到分组结构。

### 3. `commands.rs` 约 613 行

建议拆成命令层和服务层：

- `commands/extraction.rs`
- `commands/filesystem.rs`
- `commands/project_tools.rs`
- `runtime/task_registry.rs`
- `runtime/target_lock.rs`

Tauri 命令函数应只做参数校验和服务调用，不承担复杂流程。

### 4. 平台能力没有形成统一模型

Claude 启动在非 Windows 平台由后端返回错误，但前端没有在渲染前获得能力信息。建议新增 `get_runtime_capabilities`：

```text
platform
supportsClaudeLaunch
supportsRar
supportsNativePause
supportsOpenTerminal
```

界面可据此显示正确状态，而不是依赖失败路径。

### 5. 深度监听整个工作区并同步写 localStorage

`channels.ts` 对通道和设置做深度监听，再节流写入。随着任务和日志增长，序列化会造成主线程抖动。建议：

- 工作区配置继续使用小型 JSON；
- 任务历史、错误详情和 manifest 索引迁移到 SQLite；
- 使用显式 action 标记脏状态，而不是深度监听所有字段。

### 6. 测试以源码标记检查为主

现有脚本能防止关键字符串丢失，但无法证明交互和业务行为正确。建议增加：

- Vitest：目录解析、状态迁移、任务规划；
- Vue Test Utils：按钮可用性、空状态、忙碌状态；
- Rust 单元测试：DAT 生成、路径校验、能力返回；
- Playwright/Tauri 驱动：选择目录 → 生成 DAT → 启动失败/成功提示。

### 7. 缺少锁文件

源码包中没有 `package-lock.json` 和 `Cargo.lock`，同时依赖使用范围版本。发布构建可能随时间得到不同依赖组合。应用项目应提交两个锁文件，并在 CI 使用 `npm ci` 与 `cargo build --locked`。

### 8. CSS 仍有多个超大文件

`base.css`、`settings.css`、`workspace.css` 体积较大。建议按组件或语义拆分，并建立 tokens 层，避免选择器覆盖顺序成为隐式依赖。

## 下一版本建议

### 推荐版本：0.8.2“可用性与可发布性”

必须完成：

1. Windows CI 与锁文件；
2. 运行时能力检测和 Claude 状态卡；
3. 统一操作可用性/禁用原因模型；
4. 应用内确认对话框；
5. Claude DAT 与目录选择的组件测试；
6. 拆出 `taskRuntime.ts` 和 `workspacePersistence.ts`。

完成这些后再进入 0.9.0。0.9.0 可聚焦“归档预览与选择性解压”，持续目录监控放到后续小版本，避免一次引入过多后台状态与文件系统边界问题。
